## What each action does

| Action | Engine |
| --- | --- |
| `retry` | Starts the issue over from nothing: new worktree, new developer session |
| `switch-vendor` | The same, with every agent's vendor swapped. Codex reviews what Claude develops |
| `split` | Writes the smaller issues as `plans/<plan>-split-<n>.yaml` on a branch and opens a pull request into `main` |
| `research` | On the menu in the doc. Refused until a research step exists |
| `escalate` | `blocked` label, and the issue shows in `factory blocked` |

What code enforces, each covered by a test:

- **An answer off the menu is `escalate`.** A stand-in judgment that answered "merge-anyway" got a person, not a merge.
- **A judgment can't extend its own budget.** With no new attempts left, `retry` is overruled and the prompt for that call already says it is unavailable.
- **A split creates nothing.** It becomes a plan pull request, which goes through `plan-validate` and a person's merge like any plan. An invalid split goes back to the LLM once with the validator's errors.
- **A new attempt cleans up after the old one.** It closes the pull request and deletes the branch the earlier attempt left.

| Question | Answer |
| --- | --- |
| Who rules on a flow-change-request: the judgment step, or the acceptance writer | Still the acceptance writer, as decided in step 3. The judgment step is only called when a run is stuck |

## Where the build differs from the design doc

- **`retry` and `switch-vendor` start from nothing.** The doc does not say whether a retry continues the attempt or replaces it. Starting over keeps the judgment's promise that context never drifts, and it means every gate runs again.
- **A split is a proposal, not a creation.** The doc has the task manager create the new issues through the plan create path. Here that path starts where it does for a person: a plan file in a pull request into `main`. An LLM-written plan gets the same review as any other.
- **The judgment is called at one point only: a stuck run.** The doc lists three more places a judgment could help: a reviewer the developer disagrees with, a diff outside scope, and whether to research first. Those are still rules or not built.
- **Its vendor is not constrained.** It may share a vendor with the developer. It does not judge the code, it decides what happens next.
- **Attempts are counted in the running process.** A person's `factory retry` starts the count again.

## Problems hit

1. **The real agents are hard to get stuck.** The first design for a real judgment run was a check with a hidden rule. Codex read the checker's source outside the repository and worked the rule out. The check had to be made impossible, and Codex then diagnosed that too.

## Open items

- **`retry`, `switch-vendor` and `split` have only run with stand-ins.** The one real judgment chose `escalate`.
- **Nothing closes the original issue after a split is merged.** The pull request's text asks the person to.
- **`research` is on the menu and does nothing yet.**
- **A dropped issue stays open with no label saying it was dropped.** Only a comment says so.
- **The app's judgment queue is `factory blocked`** until the app exists.
