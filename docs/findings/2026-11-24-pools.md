# Findings: resource pools (2026-11-24)

`factory capacity` could say that this machine fits three simulator steps at once. The engine still ran one. Pools make the engine use the number.

## Result

It works, with tests and one real check. It also turned up a fault that was there before pools: two issues could merge at the same moment, and the second landed on code it had never been verified with. That is fixed.

| | |
| --- | --- |
| Built | Pools in `~/.factory/config.yaml`, counted slots, `factory capacity --write` and `--prepare`, a slot-aware `verify.sh` in the template and the trial repo |
| Tested with stand-ins | 40 scenarios. Three are new: a simulator pool of 2 with three issues, the queue sizing itself from the pool, a vendor pool of 1 |
| Run for real | Three `verify.sh` runs at once on the trial app, each told only its slot number, twice. All six passed 8 of 8 flows, each on its own simulator. `factory capacity --write` against a scratch folder, and `--prepare` creating a fourth simulator |
| Not run for real | A queue of three real issues through the engine with a pool of 3. The trial repo has no open issues left, and a new plan needs a person to merge it |

## How it works

- **A pool is a name and a number of slots**, counted across every project on the machine. A slot is a lock file, `~/.factory/locks/<pool>-<slot>.lock`, held with the operating system's file lock. Taking a slot means trying each file in turn until one is free.
- **A check step takes one slot of every resource its module lists in `locks`** and holds it while its command runs. With no config a pool has one slot, which is the old behavior.
- **An agent call takes a slot of its vendor's pool,** if the config names one, for that call only. A call that waits out a usage limit gives the slot back first.
- **The command is told its slot,** as `FACTORY_SLOT_SIMULATOR=2`. The engine does not know what a simulator is. `verify.sh` maps slot N to the simulator named `factory-sim-N`.
- **The queue runs as many issues as the simulator pool holds,** when `--parallel` is not given, and never fewer than 2.

## The real check

Three fresh checkouts of the trial app, three `verify.sh` processes started together, given `FACTORY_SLOT_SIMULATOR` 1, 2 and 3 and nothing else.

| Slot | Simulator it chose | Flows | Simulators shut down before | Simulators already booted |
| --- | --- | --- | --- | --- |
| 1 | `factory-sim-1` | 8 of 8, both times | 333 s | 286 s |
| 2 | `factory-sim-2` | 8 of 8, both times | 322 s | 287 s |
| 3 | `factory-sim-3` | 8 of 8, both times | 327 s | 277 s |
| One verify alone, as a control | `factory-sim-1` | 8 of 8 | | 197 s |

**Three at once cost more this time than in the first measurement.** Alone, a verify took 197 s, the same as this morning's 196 s. Three at once took 277 to 287 s each, 41 to 46% longer, where the morning's measurement had 206 to 219 s, 12% longer. Same app, same commit, same machine. The cause was not isolated. Another session was working on this machine during the second measurement, and a fourth simulator had just been created.

| | Morning | Afternoon |
| --- | --- | --- |
| One verify alone | 196 s | 197 s |
| Three at once, each | 206 to 219 s | 277 to 287 s |
| Verifies per hour, three at once | 49 | 38 |
| Against one at a time (18 per hour) | 2.7 times | 2.1 times |

So three slots are worth between 2.1 and 2.7 times one, not a fixed 2.7. A pool of 3 is still right for this app on this machine.

**A simulator that has to boot costs about 45 seconds.** That is the gap between the two columns. Any boot, not only the first, keeps the machine busy for about a minute: a used simulator booted with nothing else running took the CPU from 2% idle back to 86% in 75 seconds. `verify.sh` leaves its simulator booted, so only the first verify after a restart pays.

## `factory capacity --write` and `--prepare`, for real

- **`--write`,** against a scratch folder holding a `handoffs:` line: it wrote `simulator: 3`, `codex: 2`, `claude: 2` and kept the line.
- **`--prepare`** with a pool of 4: it found `factory-sim-1` to `3`, created `factory-sim-4` on iOS 27.2 as an iPhone 17, booted it, and shut it down. The simulator took 2.4 GB of disk. It was deleted afterwards.
- **The first version waited its full 480 seconds and then said "ready".** It waited for the CPU to be 70% idle, and this machine sat at 68% idle with nothing of the engine's running. It now compares with how idle the machine was before the boot, and says so when it gives up. The second try was ready after 75 seconds. Booted once more by hand, that simulator behaved like a used one.

## The fault it found: two merges at once

The new scenario with three issues failed about one run in three, with the third issue refused at merge. The cause was not in the pools.

- **What happened.** Before merging, a run checks that the base branch has not moved. Two runs made that check at the same moment, both saw an unmoved branch, and both merged. The second merge put a branch onto a `dev` it had never been built or verified with.
- **Why it had not shown.** The stand-in GitHub crashed on the second merge by accident of how it was written. The real GitHub accepts it, silently. The queue trial earlier today ran two issues and did not hit the moment.
- **Made visible.** The stand-in now takes merges one at a time, as GitHub does, and records every merge of a branch that lacks the latest `dev`. Every queue scenario fails on such a record. With that in place the old two-issue scenario failed too, on every run.
- **The fix.** The last look at the base branch and the merge now happen under one lock per repository. Five runs of all 40 scenarios passed after it, where six of six failed before.
- **What it does not cover.** A person, or a second machine, merging in that same moment. A GitHub branch rule that requires branches to be up to date closes that, at the price of more waiting.

## Problems hit

1. **The first assertion looked for the slot message in the wrong place.** Each issue's output goes to its own log file, not to the queue's output.
2. **The other session's work landed in the same checkout.** Unit tests went from 94 to 105 between two runs, because a second session was adding provider code to the same files. The pool commit holds only the pool changes, and was built and tested in a clean checkout before it was pushed.
3. **Two assertions assumed timing.** "All three verifies overlap" and "all three developers start before one ends" are likely, not certain, on a loaded machine. They now check what must hold: never more in use than the pool has, never one slot held twice, and the queue's own start and end lines.

## Open items

- **No real engine run with three slots yet.** It needs three open issues with separate scopes on the trial repo, so a plan pull request into `main`.
- **This machine's config is not written.** `factory capacity --write` was tried against a scratch folder only. Until someone runs it here, the engine runs one simulator step at a time, as before.
- **The pools are per machine, not per project.** Two projects share them, which is the point, but nothing yet decides which project goes first. That is the scheduler.
- **A long build changes the numbers.** The proposal of 3 comes from an app that builds in seconds.
- **Slot 1 falls back to a plain simulator when `factory-sim-1` is missing.** Convenient with no pools. With a pool above 1 and no `--prepare`, slot 1 works and every other slot fails with a message that says what to run.
