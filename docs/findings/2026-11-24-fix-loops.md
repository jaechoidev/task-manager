# Findings: fix loops (2026-11-24)

Build-order step 4: fix loops for local review and verify, with round limits. Tried on `jaechoidev/todo-trial` issue #6, on a local scratch repository with real agents, and in automated tests that run the real engine against stand-in agents.

## Result

A failure the developer can fix now sends the issue back to it. The developer continues its own session and is told what failed. Verify and a fresh review then run again on the new commit. Three rounds by default, five at most, and the issue ends `blocked` when they run out.

| Where | What ran | Outcome |
| --- | --- | --- |
| todo-trial issue #6 | Real Codex and Claude, real simulator | Passed on the first try, no fix round. [todo-trial#16](https://github.com/jaechoidev/todo-trial/pull/16), merged |
| Local scratch repo | Real Codex and Claude, `gh` replaced by a script | Verify failed, one fix round, passed. 1 minute in total |
| `tests/fix_loop.rs` | The real engine, git, gates and `verify.sh`, with scripts for the three CLIs | 6 scenarios pass |

The real fix round, step by step:

| Step | Result | Time |
| --- | --- | --- |
| develop (Codex) | Wrote the function. Could not run verify in its sandbox | 18 s |
| verify | Failed: a lint line the developer could not have known | under 1 s |
| develop, fix round 1 (Codex, same session) | Added the line, changed nothing else | 14 s |
| verify | Passed | under 1 s |
| review (Claude) | approve | 12 s |

The six automated scenarios: a failed verify, a review asking for changes, a change outside scope, rounds running out, an accepted flow change request, and a rejected one. The last two also close the open item from the acceptance stage: the ruling had never run.

## Answers to the design doc's open questions

How each CLI continues a session, which the doc asks for under "Dev resumes the same session":

| | Codex | Claude |
| --- | --- | --- |
| Command | `codex exec resume <id> ... -` | `claude -p --resume <id> ...` |
| Session ID after resuming | Unchanged | Unchanged |
| Output schema on the resumed call | `--output-schema` works | `--json-schema` works |
| Sandbox | `exec resume` has no `--sandbox` or `--cd`. `-c sandbox_mode="workspace-write"` sets it, and it holds | Permission flags are given again on each call |
| Remembers the earlier call | Yes | Yes |

If a session can't be continued, the engine starts a new one with the same prompt. The fix prompt restates the scope, the criteria, the IDs and the rules, so it works either way.

## A security problem, found and fixed

**Claude was never confined to the worktree.** Since step 2 the engine called Claude with `--permission-mode acceptEdits --allowedTools ... Write`, and the code comments said that limits writes to the worktree. It does not. In a direct test, Claude with those flags wrote a file outside its directory. The acceptance writer ran that way on todo-trial issue #5. Nothing suggests it wrote anything outside: its reports and the git diff show only the flow file. But nothing prevented it.

What changed:

- Every Claude call now carries `permissions.blockWritesOutsideWorkingDirectories` and `permissions.blockReadsOutsideWorkingDirectories`. With both, the same test is refused for reads and for writes.
- The reviewer no longer has any shell. It had `git diff`, `git log` and `git show`, and `git diff --output=FILE` writes a file anywhere.
- A Claude writer may no longer run `./verify.sh`. It could edit that script first and so run any command.

Codex's sandbox did hold in the same test, including on a resumed call. It can still read any file on the machine. Its replies end up in pull request bodies, so a hostile issue or file could in principle make it copy something there.

## Other findings

- **Real agents have not needed a fix round on the trial app.** Four real issue runs so far, four first-try passes, even though Codex cannot run the simulator. The first scratch task built to fail also passed: Codex saw a header convention in a neighbouring file and followed it. The failure had to be something no file could reveal.
- **A fix round is cheap when the failure message is specific.** 14 seconds, one line changed, nothing else touched.
- **The CI review also approved #16.** Both reviewers pointed out the same gap: no flow checks that a done todo is struck through, because the accessibility tree does not expose text style. The flow uses the toggle's selected state instead. A screenshot taken by hand shows the strikethrough is there.
- **An older state database upgrades in place.** The `steps` table gains a `round` column on first open.

## Where the build differs from the design doc

- **No brief yet.** The doc has an LLM compress logs and reviews into a short brief for each fix round. Here the developer gets the last 120 lines of the failed check (12,000 characters at most) and the reviewer's items as written, numbered R1, R2 and so on. The doc says to settle the brief by measuring fix rounds with and without it, and this is the "without" baseline.
- **Running out of rounds ends in `blocked`,** not in the Judgment step, which is not built.
- **Only rounds are capped.** Time per issue and calls per day are not.
- **One shared limit.** The doc gives local and GitHub rounds separate limits. There is no GitHub loop yet.
- **A red check that fails still stops the run.** `on_fail: red: acceptance` is accepted in the workflow file, but only a return to the developer is built.
- **Some failures are never retried:** a developer that changes no files, a check that times out, an unusable reply twice in a row, a reviewer naming the wrong commit.

## Problems hit

1. **Claude's confinement**, above.
2. **`codex exec resume` takes fewer flags than `codex exec`.** Without the config override, a resumed developer would have run with whatever sandbox the user's config sets.
3. **Issue #6 had the same narrow scope as #5** and was widened by hand the same way. Issues #7 and #8 still have it. The scopes that would work for #6 and #7 both include the list screen, which the plan validator would only allow if one depended on the other.

## Open items

- **No fix round has happened on the iOS project.** The developer has not yet been handed a failed Maestro flow. The message format is tested, the usefulness of Maestro's output to a developer is not.
- **A broken environment burns fix rounds.** Verify cannot say "I could not run" as distinct from "the code is wrong". A dead simulator would send the developer back three times for nothing.
- **Nothing checks that each review item was addressed.** The items are numbered, the next reviewer sees them, and that is all.
- **A reviewer can still ask for something new each round.** The prompt tells it not to, and the round limit bounds the cost.
- **Rate limits are still recorded as failures,** not as waiting.
