# Findings: one issue end to end (2026-11-24)

`factory run 4` took issue [todo-trial#4](https://github.com/jaechoidev/todo-trial/issues/4) from nothing to an open pull request, [todo-trial#11](https://github.com/jaechoidev/todo-trial/pull/11), in 68 seconds, on the first attempt.

| Step | Who | Result | Time |
| --- | --- | --- | --- |
| develop | `codex exec`, workspace-write sandbox | Replied with a valid report. 2 files changed | 40 s |
| history, locked-flows and scope gates | engine | Passed | under 1 s |
| commit | engine | `d2523d4` | under 1 s |
| verify | `./verify.sh`, build only | Passed | 4 s |
| review | `claude -p`, read-only | approve, on the same commit | 18 s |
| push and pull request | engine | Opened into `dev` | 4 s |

The run used the MacBook as `jaechoidev`, not the Mac Studio as `neostudiodot`.

## Answers to the design doc's open questions

**How each CLI returns structured output reliably.** Both do it natively, with no prompt tricks:

- `codex exec --output-schema <file> -o <file>` writes the final message as JSON matching the schema. `--json` streams events, and the first one carries the thread ID for a later resume.
- `claude -p --output-format json --json-schema <schema>` prints one result object. The reply is in `structured_output`, and `is_error` says whether the call failed.

The engine still parses each reply into a typed struct that rejects unknown fields, and retries once on a mismatch.

**How each CLI handles workspace trust in a fresh worktree.** Neither asked anything. Both ran headless in a worktree created seconds earlier.

**Vendor pair.** Codex develops, Claude reviews. The workflow loader rejects a reviewer from the developer's vendor.

**Reuse Teamflow's worktree handling?** Not needed so far. `git worktree add -B <branch> <path> origin/<base>` plus a prune is enough for one issue at a time.

## Other findings

- **The sandbox did not stop Dev from building.** Codex ran `./verify.sh` inside the workspace-write sandbox and it passed. The engine's own verify run is still the one that counts.
- **A headless `claude -p` call carries a large fixed cost from user settings.** A one-file probe reported a notional 1.12 USD with the user's MCP servers, plugins and skills loaded, and 0.67 USD with `--strict-mcp-config --setting-sources project,local --disable-slash-commands`. The engine uses the lean form.
- **Synchronized folders keep scopes clean.** `Sources/` is a file-system synchronized group in the Xcode project, so Dev added a Swift file without touching the project file, which is outside every issue's scope.
- **The reviewer found something the gates can't.** `.maestro/sample.yaml` asserts the ID `app.root`, which this change removes. Dev may not edit flows and raised no flow change request. That smoke flow will fail once Maestro runs. It needs an owner: the acceptance stage should replace it.
- **The engine made the CI build slower, not broken.** Project workflows compile `factory` on a Linux runner. With SQLite compiled in, a cold `plan-create` run takes 112 s, up from 84 s. Cached runs are unaffected.
- **Refusals work without any agent call:** a blocked issue (#5 while #4 is open), a parent issue (#3), and a rerun while the issue's branch is still on GitHub.

## Where the build differs from the design doc

- **Agents are sandboxed and the engine owns git.** The doc assumed permissions bypassed. Dev writes only inside its worktree. Review is read-only. Neither gets git or network commands.
- **Verify is build only.** Maestro is not installed on this Mac. It joins at the acceptance stage.
- **No daemon, no HTTP API, no tokio.** The loop is a sequential CLI command. `factory status` reads the database directly. The API is still to be designed for the app.
- **The workflow is read from the default branch,** not from a working copy, so a run always uses reviewed files. `--workflow <file>` overrides it for trials.
- **`factory.yaml` lists three steps.** The scope gate, the lock on `.maestro/` and the pull request are engine behaviour, not modules.

## Problems hit

1. **The first `review.yml` run failed with 401.** The `CLAUDE_CODE_OAUTH_TOKEN` stored on the trial repo is rejected as invalid. The workflow itself ran correctly up to the API call. It failed on every pull request into `dev` until the secret was set again. The cause was a bad copy of the token, twice. Testing the token locally first (`CLAUDE_CODE_OAUTH_TOKEN=... claude -p "say ok"`) and piping it into `gh secret set` fixed it.
2. **A temporary debug line reached `dev`.** While reading that failure I added `show_full_output: true` to `review.yml` on the setup branch. My revert did not push, and the squash merge of [todo-trial#9](https://github.com/jaechoidev/todo-trial/pull/9) carried the line into `dev`. [todo-trial#10](https://github.com/jaechoidev/todo-trial/pull/10) removed it.
3. **The trial repo's `factory.yaml` named modules that don't exist yet.** The engine rejected it before starting, as intended. #10 also replaces that file.

## The CI review, once the token worked

With a valid token the `review` check on [todo-trial#11](https://github.com/jaechoidev/todo-trial/pull/11) went green and commented a verdict on the same commit.

1. **A green check is not an approval.** The check passed and the comment says "Verdict: changes". The workflow succeeds when the review ran, whatever it concluded. The GitHub loop has to read the verdict from the comment, or the workflow has to fail on "changes".
2. **Two reviewers disagreed on the same commit.** The engine's reviewer approved and listed the broken `.maestro/sample.yaml` for a human. The CI reviewer asked for changes because that flow is broken and the issue's acceptance flow (`launch_empty.yaml`) does not exist. Neither found a code bug. Both gaps belong to the acceptance stage, which is not built.
3. **The CI reviewer could not read the issue.** `review.yml` had no `issues: read` permission, so `gh issue view` failed and it fell back to the plan file. Fixed in the template, and in [todo-trial#12](https://github.com/jaechoidev/todo-trial/pull/12). Not yet verified on a pull request that links an issue.

## Open items

- **No failing run has been exercised end to end.** Gate functions, the process timeout and the workflow checks have unit tests. A real run where verify fails, review asks for changes, or Dev leaves scope has not happened yet.
- **Nothing merges.** The run ends at an open pull request. Polling CI and review on the head SHA, then merging to `dev`, is the GitHub loop step.
- **Rate limits are not detected.** A CLI exit caused by a usage limit is recorded as a failure, not as waiting.
- **Locks are declared, not enforced.** `locks: [simulator]` is parsed. With one issue at a time nothing contends for it.
- **`subscription` in the request log is always `default`.** Only one account per vendor exists so far.
- **Dev does not resume a session.** There is no fix loop, so nothing to resume. Session IDs are recorded for when there is.
- **A rerun needs manual cleanup.** The engine refuses to run an issue whose branch is still on GitHub.
